Unreleased — 0.7.0 Safe Updater Foundation

Status
- Active candidate version: 0.7.0.dev0.
- Implementation and Windows live updater validation are complete for the 0.7.0 scope.
- The public v0.7.0 tag/release has not been created yet.

Safe update architecture
- DDSUpdater.exe runs as a separate external updater process; DDS never overwrites its running payload.
- DDS.exe is the stable bootstrap; application payloads live under versions/<version>.
- current.json selects the active version, previous.json records the previous successfully-started version, and pending_update.json makes promotion transactional.
- A candidate is committed only after startup acknowledgement; failed startup automatically rolls back.
- Startup acknowledgement is tied to core runtime readiness, not completion time of the initial full archive import.
- Startup commit is idempotent and repairs the crash window where pending state reached disk before current.json switched.

Integrity and isolation
- Versioned release manifest: channel, asset, SHA-256, exact size, updater protocol and package format.
- Atomic partial download promotion only after exact size and SHA-256 verification.
- ZIP validation rejects traversal, drive paths, symlinks, Windows case collisions and protected user-data roots.
- Staging verifies the package and DDS.install.json before promotion.
- SQLite/archive, settings, media/cache, exports and DDS_Data are outside updater ownership.
- Tests prove user-data sentinels remain byte-identical after both success and forced rollback.

Recovery and observability
- Cross-process update.lock prevents concurrent update ownership.
- Free-space guards run before download/staging and before install.
- updater.log records promotion, startup confirmation and rollback.
- journal.json records durable updater lifecycle states.
- Power-loss handoff between pending/current pointers is recoverable.
- Launcher startup removes orphaned non-authoritative version directories and stale .incoming-* trees after interrupted promotion.
- Failed Windows candidates are terminated as a process tree and removed with bounded retry.
- Rollback preserves the already-committed previous working build and relaunches the restored version.
- Release/download operations use bounded timeout/retry and cancellation cleanup.

Update UX
- Settings provides manual check/download/install flow.
- Optional background checking is bounded to at most once per day.
- Daily background update throttling counts attempts, not only successful GitHub responses, so outages do not cause a check on every DDS launch.
- Automatic install remains opt-in; update/network failure never blocks archive use.
- Release notes are normalized and bounded before display.
- Updater protocol/package format are versioned and fail closed on unsupported formats.

Validation completed on Windows
- Full unittest discovery: 174/174 PASS, three consecutive runs.
- compileall PASS.
- Native PyInstaller build PASS for DDS.exe, DDSApp.exe and DDSUpdater.exe.
- Live success PASS: dev0 -> synthetic dev1, startup ACK, journal COMPLETE, STARTUP_CONFIRMED, previous=dev0.
- Live forced-timeout rollback PASS: dev1 -> broken dev2 -> watchdog rollback; current=dev1, previous=dev0, failed dev2 removed, no dev2 processes remain, journal FAILED, ROLLBACK_COMPLETE.
- Test sandbox returned to a clean 0.7.0.dev0 application baseline.
